# Drawdown checks at the Paper execution boundary

The existing scheduler pauses active non-hold accounts when observed portfolio equity falls below the configured high-water drawdown threshold. It checks equity on startup and periodically every minute. Its peak/status are persisted in the application database. This periodic pause alone did not prevent a broker entry arriving before the next scheduler check.

Three actual Paper-broker regression tests reproduced accepted entries that should have been blocked: an already-breached persisted peak while status remained active, a breach appearing during simulated latency, and an otherwise-permitted entry whose known spread/fees would put the account beyond the limit. The regressions used the existing separate test database and synthetic books/account values; no production account breach or real trade is claimed.

`entryDrawdownGuard` now checks finite nonnegative equity, a finite positive persisted peak and a fraction-valued existing limit. It compares against max(current equity, persisted peak). The non-hold buy path applies it before sizing, again against freshly read account/equity after latency, and against calculated post-fill equity before the database transaction. This uses the existing `MAX_DRAWDOWN_PCT`, with no new parameter, strategy or model. The high-water mark is not reset by broker construction/restart. Explicit existing account resume remains a user action and retains its existing peak reset semantics.

Entry rejection does not itself clear or rewrite account status/peak. The scheduler remains responsible for its persisted paused status. Protective sells continue through the separate sell path even if the drawdown is breached or the account is paused. Buy-and-hold remains the pre-existing explicitly unprotected benchmark exception. Gaps, missing/stale books and order execution can still cause losses beyond the configured threshold; it is not a guaranteed loss cap or liquidation price.

Historical portfolio replay applies the same pre-transaction post-fill drawdown gate. This avoids comparing a stricter Paper executor against a replay that permits known cost-induced breaches. A fixed synthetic replay with deliberately tiny drawdown allowance rejects the entry, leaves cash at100, charges no fees and records a rejection. This is a contract test, not a useful trading parameter or optimization candidate. Historical results generated under older execution versions remain intact; any future economic comparison must identify the changed execution semantics and run the unchanged baseline separately.
