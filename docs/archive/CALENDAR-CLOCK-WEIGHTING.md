# Calendar-clock recency weighting

Pinned Freqtrade FreqAI sources provide a useful separation: data_kitchen.py creates optional recency sample weights, LightGBMRegressor.py passes training/evaluation weights to its model, and freqai_interface.py optionally supplies an existing model for continual learning. Weighting, refitting and warm-starting are different operations. Existing sources were revisited at commit7fea5ea24b3c3193cfdd4143b243f7baab66d661 (GPL-3.0); no framework code/model/dependency was imported, executed or installed.

The upstream weight helper is based on row positions in the supplied frame. That is not automatically elapsed calendar age for our pooled20asset corpus: the same timestamp has many asset rows, order is not recency, and an unknown label may leave19rather than20rows. This is a local adaptation concern, not a universal upstream defect.

Own optional `calendarClockWeights` validates unique pair/clock identities and labels strictly mature before training. It assigns a shared clock's age from its latest label maturity, exponential base-two decay with explicit calendar half-life, equal total pre-decay clock mass, and equal row weights within a clock. The resulting positive weights are normalized to mean row weight1, preserving the existing numerical loss-mass/regularization convention. This does not estimate independent sample count. Weight construction never reads feature or payoff values. Invalid/future clocks, duplicates, nonpositive decay or numerical underflow reject the fit.

`fitRidge` now optionally accepts positive finite sample weights and uses them consistently for means, population scales, unpenalized target intercept and ridge normal equations. Default behavior is unchanged. `fitBarrierRidge` optionally builds calendar weights after validating all targets and retaining ambiguous-label counts. A weighted model seals method/half-life/shared-clock count/weight hash into its existing model integrity hash.
